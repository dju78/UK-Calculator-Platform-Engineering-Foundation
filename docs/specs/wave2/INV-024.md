## Purpose

Show the effect of fund and platform charges on a long-term investment.

## Scope

A fund holding with an ongoing charge and an optional platform fee.

## Assumptions

- Charges accrue monthly on the running balance, which is how ongoing charges actually work.

## Inputs

| Name | Label | Type | Default | Units / notes |
|---|---|---|---|---|
| `initial_investment` | Initial investment (£) | number | 10000 | - |
| `monthly_contribution` | Monthly contribution (£) | number | 200 | - |
| `gross_return` | Gross annual return (%) | number | 7 | - |
| `ongoing_charge` | Ongoing charge (%) | number | 0.22 | The fund's OCF, e.g. 0.22 for 0.22%. |
| `platform_fee` | Platform fee (%) | number | 0.25 | - |
| `years` | Years | number | 20 | - |

Percentages are entered as human percentages (5 means 5%) and normalised once
inside the engine.

## Validation

Enforced centrally at the engine boundary and by the shared validation module:

- Any non-finite input is rejected with a readable message.
- Any non-finite output is rejected rather than returned, so `NaN` and
  `Infinity` can never reach a user.
- Terms are bounded (maximum 150 years) and monetary amounts capped, so no
  input can spin an amortisation loop indefinitely.


## Formula and logic

Two parallel monthly simulations - gross and net of charges - differenced to give the fee drag.

## Outputs

- `gross_value`
- `net_value`
- `total_fees`
- `total_contributions`
- `fee_drag_percentage`
- `net_annualised_return`

Formatting is decided by the central registry in
`apps/web/src/components/calculators/outputFormats.ts`, per calculator and per
key, so ratios render as percentages and money as `£1,234.56`.
